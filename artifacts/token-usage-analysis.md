# Part 2：上下文压缩与完整上下文对比

本次实验使用 `deepseek-flash`，任务为 `django__django-15368`，基础提交为 `e972620ada4f9ed7bc57f28e133e85c85b0a7b20`。压缩版的触发阈值为 6,000 token，保留最近一个完整步骤；baseline 关闭压缩。两组使用相同任务、工具和 sandbox 镜像，但由模型独立选择行动。

压缩版此前已通过 `check-swebench`。本次 baseline 也通过检查：`FAIL_TO_PASS` 为 1/1，`PASS_TO_PASS` 为 29/29，结果为 `RESOLVED: yes`。Baseline 的检查输出保存在 [检查日志](django__django-15368-baseline-check.log) 中；压缩版的通过依据是此前运行的反馈，未另存对应检查日志。

## 统计结果

数据来自 [压缩版轨迹](django__django-15368-trajectory.json) 和 [baseline 轨迹](django__django-15368-baseline-trajectory.json)。输入、输出均使用 API 返回的 `usage`，而不是字符数估算。

| 指标 | 压缩版 | 无压缩 baseline |
|---|---:|---:|
| 行动请求次数 | 24 | 28 |
| 摘要请求次数 | 7 | 0 |
| 模型请求总次数 | 31 | 28 |
| 行动请求输入 token | 94,983 | 411,985 |
| 行动请求输出 token | 4,507 | 6,292 |
| 摘要请求输入 token | 32,227 | 0 |
| 摘要请求输出 token | 6,822 | 0 |
| 输入 token 合计 | 127,210 | 411,985 |
| 输出 token 合计 | 11,329 | 6,292 |
| 输入与输出 token 总计 | **138,539** | **418,277** |
| 单次行动请求输入峰值 | **5,927** | **25,552** |

统计时，将 `responses` 中的行动请求与 `compactions[*].compaction_response` 中的摘要请求分别求和，再相加。`completion_tokens` 已包含记录的 reasoning token，不能重复加入；缓存命中的输入也属于 `prompt_tokens`，不能再加一次。

## 上下文变化及原因

Baseline 的每次行动请求都携带完整历史，输入从第一步的 1,466 token 增长到最后一步的 25,552 token。压缩版的历史则周期性被替换为工作记忆与近期完整交互，单次行动请求输入维持在 1,466～5,927 token。

轨迹记录了 7 次压缩，每次压缩前后的消息 token 估算值均下降，降幅为 7.7%～67.2%。例如，第 6 步之后从 4,163 降至 1,364，第 8 步之后从 6,385 降至 2,362。这里使用的是压缩事件中的粗估值，与触发阈值所用的校准估算以及 API 返回的实际用量不是同一个指标。

压缩后仍然保留近期完整步骤，因此不能消除近期工具结果的全部长度。部分事件降幅较小是合理的；要保持工具调用与观察的关联，就必须保留这些消息。

计入摘要请求的额外开销后，本次压缩版的输入 token 合计减少 **69.1%**，输入与输出总计减少 **66.9%**，单次行动请求输入峰值减少 **76.8%**。这些结果说明本次运行降低了工作上下文的大小，也减少了记录到的总 token 用量。

## 额外开销与缓存

压缩不是免费的。7 次摘要请求额外消耗 32,227 个输入 token 和 6,822 个输出 token，使模型请求总次数增加到 31 次；总输出 token 也高于 baseline。

缓存统计进一步显示，token 总量和实际费用需要分开判断：

| 输入 token 分类，包含摘要请求 | 压缩版 | 无压缩 baseline |
|---|---:|---:|
| 命中缓存 | 73,856 | 391,552 |
| 未命中缓存 | **53,354** | **20,433** |
| 缓存命中比例 | 58.1% | 95.0% |

虽然压缩版总输入更少，未命中缓存的输入却约为 baseline 的 2.61 倍。一个合理解释是：完整历史不断追加，已有请求前缀更容易复用；摘要会改写历史前缀，摘要请求本身也会引入新的输入。两次运行的具体行动不同，同样会影响缓存，因此不能将全部差异归因于压缩。

本报告没有结合缓存命中、未命中及输出的实际计费单价计算金额，也没有测量端到端延迟。因此，不能把总 token 减少 66.9% 解释为费用或耗时也减少 66.9%。

## 结果的适用范围

两组补丁都解决了 `bulk_update()` 对可解析表达式识别过窄的问题，本次实验没有观察到摘要丢失信息导致任务失败。摘要仍可能遗漏文件、约束或验证结果；一个任务通过不能证明其他任务也安全。

本次压缩版用了 24 次行动请求，baseline 用了 28 次，但这只是每个条件各一次独立运行。生成和工具选择存在随机性，不能据此断言压缩会稳定减少行动步数。更可靠的结论是：本次实现确实触发了压缩、缩短了上下文，并完成了任务；更一般的收益还需要多次实验验证。

## Recap

本次压缩在任务通过的同时降低了上下文峰值和总 token 用量，但增加了摘要调用、总输出及未缓存输入。选择是否压缩，应同时考虑上下文容量、任务可靠性、摘要开销和缓存效果，不能只看总 token 数。
